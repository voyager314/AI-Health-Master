## Context

PRD v0.5 把数据模型收窄到 6 张业务表，现有的数据地基按旧模型写成。本 change 的现状约束有四条：

1. **没有写入旧表的代码路径。** 现存命令只有 `app_meta/mark_exported`、`app_meta/grant_consent`、`data/import`、`data/clear_all`，四张待删表从未被业务写入。删表因此不需要迁移数据，只需要改结构。
2. **环境中的数据尚未对外发布。** 库结构版本保持 1，直接改写这条迁移的内容；已在本地打开的旧库不会被自动升级，需要使用者清除一次站点数据。
3. **存储层已在 `storage/indexeddb/**` 内收敛。** 改动集中在实体契约、建表定义与测试夹具，页面只有一个读取点需要跟着改名。
4. **导出结构等于内部结构。** 表清单是在 `entities` 里的一处常量，导入、导出、路由与测试都从它派生，收敛也随之由一处驱动。

## Goals / Non-Goals

**Goals:**

- 业务表收敛到 PRD §10.1 的 6 张，运动项目作为 `workout_log` 的嵌套值
- 项目卡片的字段规则落在实体规格里，导入与落库共用同一份校验
- 导出 / 导入清单随之收敛到 7 张表，往返一致性在新形状上重新成立
- 注释不再引用设计文档、需求编号与 `openspec/` 路径

**Non-Goals:**

- 不实现任何界面与写入命令（记录页、列表、清理、体重、目标都不在本 change）
- 不改动 Command 总线、事务包装与审计字段注入的形状
- 不引入新的运行时依赖

## Decisions

### D1 运动项目是嵌套值，不是实体

`workout_log.items` 为 `{ name, sets, reps, weight_kg, note }[]`，顺序即数组下标。

一条项目卡片没有主键、不被任何其他记录引用、随所属记录整体读写，因此它是记录的一个属性而非独立实体。独立成表会引入三样东西：一个没人按它取数的主键、一个与数组下标重复的顺序真相源、以及删除记录时对子表的级联清理。三者都是维护成本而没有对价。

代价：项目不可被独立查询（「哪些记录含卧推」需要内存过滤）。记录量级在千条以内，内存过滤足够；真需要检索时再提取成表，届时它才真正拥有身份。

### D2 直接改写版本 1 的迁移

`MIGRATIONS` 保持一条 version 1，内容改为建 9 个 store。不新增 version 2。

理由：库结构从未对外发布，现存数据里没有任何一行旧表记录。新增一条 v2 迁移意味着永久保留一份「建 12 个 store 再删掉 4 个」的代码，只为了让开发者本地那个库自动升级——而这批开发数据本来就该清掉。

代价与处理：开发机上已存在的库停在 version 1，打开时不会触发升级，首次访问 `workout_log` 会抛 `NotFoundError`。清除该站点的浏览器数据即可，这是开发环境的操作，不构成用户侧的数据丢失。上线后 schema 一旦发布，任何结构调整都必须走新版本号——这条边界从第一个正式版本起生效。

### D3 项目卡片的校验是一个数组字段规格

`FieldRule` 新增 `itemList`：值必须是数组、非空，每个元素只接受 `name / sets / reps / weight_kg / note` 五个键，逐项按 §10.1 的规则校验，未知键报错。

放在实体规格而不是界面里，是因为导入路径不经过界面：一份被改过的导出文件若能把 `sets: 0` 或 `weight_kg: 80.3` 写进库，落库校验之后再拒绝就没有意义了。校验要一次报出全部问题并定位到「第几张卡片的哪个字段」。

三项指标全为 `null` 合法：用户只记得项目名时，记录仍然是完整记录。

### D4 `workout_log` 只用 `logged_at` 单字段索引

近 30 天列表与「查看更早」都是「按 `logged_at` 取时间范围 + 内存过滤」，一条 `SELECT * FROM workout_log WHERE logged_at BETWEEN ? AND ?` 即可表达。不建复合索引，也不需要游标分页。

`user_id` 照旧建索引：上云后它是分用户取数的入口，且六张业务表形状一致，少一张会让「每条业务记录都带 user_id」的自检变复杂。

### D5 保留期清理登记为例外，不在此实现

`workout_log` 保留 180 个自然日，超期记录启动时物理删除。这违反「软删除之外禁止物理删除」的字面表述，因此在规格里把它显式登记为一个例外，并把「30 天展示窗口」与「180 天保留期」写成两个独立参数。

清理的执行代码随运动记录功能实现：没有记录页时，清理没有可观察的行为，现在写只能靠单测证明它对，却无法验证它不会误删。

### D6 导出清单由一处常量派生

`EXPORTED_STORE_NAMES` 由 6 张业务表加 `analytics_event` 组成，导入只接受这份清单。旧文件里出现 `exercise` / `workout` / `workout_exercise` / `set_entry` 会被判为「不是可导入的表」并拒绝——这是期望行为：那份文件来自另一个版本的数据模型，猜测它的意图比拒绝更危险。

### D7 首页读取点改为 `workout_log`

首页只统计记录条数，改为读 `workout_log` 即可，不引入新的展示内容。导航文案从「训练」改为「运动」，与 PRD 的模块命名一致。

## Risks / Trade-offs

- **改写 v1 迁移不会升级既有库** → 开发环境清除一次站点数据；上线后结构调整必须走新版本号。已在 D2 说明。
- **`items` 是数组，不能按项目名检索** → 千条量级下内存过滤足够；提取成表的成本高于收益，且会重新引入两个顺序真相源。
- **导出文件不再接受旧表名** → 旧版本的导出文件会被拒绝导入。这是模型变更的必然结果；环境中的数据从未发布，不存在需要支持的真实旧文件。
- **`body_metric` / `meal` 不受保留期约束** → PRD §14.2 的 OP-05 尚未决定是否统一，本 change 按「只对运动记录生效」执行。

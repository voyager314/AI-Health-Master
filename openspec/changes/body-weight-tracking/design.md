## Context

动机见 proposal.md 的 Why，需求见 `specs/`。现状里有六点决定了方案的形状：

1. **`body_metric` 有表、有索引，但没有写入路径。** `measured_at` 单字段索引已经建好；`BodyMetric` 类型与字段规格也已存在，只是 `weight_kg` 只校验 1–500 的范围、不校验网格，`measured_at` 与 `note` 还没有字段注释。`/weight` 目前是占位页。
2. **周界算术只在 `stats/timeWindow.ts`。** 已有 `dayKeyOf`、`weekInterval`、`weekKeyOf`、`recentDayInterval`，缺「近 N 个自然周」的窗口，也缺两个自然日之间的天数。约束测试会扫描这个文件之外的 `getUTCDay`、`getDay` 与 `86_400_000`。
3. **按自然日分组只为运动记录写过一份。** `domain/workoutLog.ts` 的 `groupByDay` 绑定了 `WorkoutLog` 与 `logged_at`；而体重明细与当日取值需要的恰好是同一条规则。
4. **保存失败的提示写在运动卡片表单内部。** 文案按失败原因分派，再加上「导出数据」「重试」两个出口。`shared/` 只允许导入 `entities/`、`stats/`、`domain/`，而 `StorageWriteError` 经 `@/commands` 转出。
5. **按幂等键定位记录的函数是运动命令的私有函数。** 体重的三条命令需要同样的定位逻辑。
6. **0.1 的浮点算术会漂移。** 实测从 70.0 连续加 0.1，第一步就得到 `70.19999999999999`。不过，凡是以「整数 ÷ 10」构造的网格值，在 1–500 kg 范围内乘以 10 都恰为整数；`Math.round(x * 10) / 10` 对该范围内全部两位小数的半值，以及全部奇数十分位的斤值，都能给出正确的四舍五入结果。

## Goals / Non-Goals

**Goals:**

- 网格只有一份定义：规整、步进、换算、校验都从它出发，界面显示的值就是存储的值
- 当日取值、周均、分组、换算全部是纯函数，可以脱离数据库单测；周界算术仍只在 `timeWindow`
- 快速记录可以在同一页反复使用，既不吞掉第二次记录，也不因连点产生重复记录
- 断网时可以记录、修改、删除

**Non-Goals:**

- 不做交互式图表：不缩放、不拖动、不做悬停提示
- 不改实体结构、不写迁移、不新增依赖、不改命令总线的形状
- 不改运动模块的行为，唯一例外是编辑页的训练日期按记录自带的偏移展示（D12）

## Decisions

### D1 网格以「整数个 0.1 kg」为中间表示

规整、步进、换算都先落到整数十分位上，再换回 kg：

- **规整**：`Math.round(kg * 10) / 10`，四舍五入到 0.1 kg。Context 第 6 点已验证它在取值范围内对两位小数的半值都正确。
- **步进**：`(Math.round(kg * 10) ± 1) / 10`。kg 与斤两种显示都是每次 ±1 个十分位（0.2 斤 = 0.1 kg），因此两种显示共用同一个步进函数，界面只换标签。禁止在上一次的浮点结果上累加 0.1。
- **换算**：斤 = kg × 2。乘以 2 在二进制浮点里是精确的，网格值换成斤后必然落在 0.2 斤网格上。斤的输入先除以 2，再按 kg 规整。
- **显示**：两种单位都用 `toFixed(1)`。

否决「改存整数十分位（如 `weight_dg`）」：那会改动数据模型与导出格式，偏离 PRD 的 `weight_kg`，而眼下的问题只是算术漂移，不是存储形态。否决引入十进制数库：它是新依赖，而整数十分位已经足以消除漂移。

### D2 网格校验落在字段规格里，命令层只拒绝、不取整

`RECORD_SPECS.body_metric.weight_kg` 在范围之外再加一条网格判定：`Number.isInteger(value * 10)`。依据 Context 第 6 点，这个判定对每个合法网格值都成立，对漂移后的近似值则不成立。取值范围提成常量，由界面的范围提示、命令的载荷校验与字段规格共用。

命令的载荷校验复用这条规则，不另写一份。离网格的载荷在开事务之前就以 `CommandPayloadError` 被拒绝，数据库不被触碰。

命令层不替调用方规整：替它取整，界面上一个漏掉规整的 bug 就会把显示为 72.45 的值存成 72.5，而且没有人能发现。规整是界面在提交前的职责（D1），存储与命令只负责把关。

这是对版本 1 字段规格的收紧，不需要迁移：应用此前从未写入过 `body_metric`，本地库与应用导出的文件里都不可能有离网格的体重。

### D3 当日取值复用通用的按日分组

把 `groupByDay` 从 `domain/workoutLog.ts` 迁到 `domain/dayGroups.ts`，按「取记录时刻的函数」参数化：

```
groupByDay(records, instantOf) -> { day: DayKey, records: T[] }[]
```

规则原样保留：按记录自带的 `tz_offset_minutes` 归日；日序倒序；组内按时刻倒序，同一时刻再按主键倒序。运动列表改为传入 `logged_at`，分组字段由 `logs` 更名为 `records`。

当日值就是每组的第一条。「当日取最后一条」与「明细组内倒序」于是由同一个排序规则给出，不可能出现明细排在最上面的那条不是当日值的情况。

否决「为体重另写一份分组」：两份实现迟早会在主键兜底这类细节上分叉，而分叉只出现在同一秒两条记录的边缘样本上，日常使用中看不出来。

### D4 周均：先取当日值，再按周平均

```
domain/bodyMetric.ts
  normalizeKg(kg)          -> number          0.1 kg 网格，四舍五入
  stepKg(kg, direction)    -> number          ±1 个十分位
  kgToJin(kg)              -> number          kg × 2
  jinToKg(jin)             -> number          ÷ 2 后规整
  dayValues(metrics)       -> DayValue[]      每个有效日一条：该日最晚的记录
  weeklyAverages(metrics)  -> WeekAverage[]   每个有效周：有效日数，与周均（不足 3 天为 null）
```

入参都是实体数组。软删除的记录在函数内部排除，「有效」的定义因此只有一处，可以单独测试。

当日值所属的周，取那条当日值记录自己的 `weekKeyOf(measured_at, tz_offset_minutes)`。归日与归周用的是同一个偏移，一个自然日不会横跨两周。

周均在函数内规整到 0.1 kg 后再返回，换算成斤也从规整后的值出发。这样 72.33 显示为 72.3 kg 与 144.6 斤，两个读数可以互相换算。

### D5 12 周窗口与横轴位置都由 `timeWindow` 给出

```
stats/timeWindow.ts
  recentWeekInterval(now, tzOffsetMinutes, weeks) -> Interval    以 now 所在周为终点，往前 weeks 个自然周
  recentWeekKeys(now, tzOffsetMinutes, weeks)     -> DayKey[]    同一窗口内各周的周一标识，时间正序
  daysBetween(from, to)                           -> number      两个自然日标识相差的天数
```

取数用 `measured_at` 区间；随后在内存中只保留自身周标识落在 `recentWeekKeys` 里的记录。这一步同时处理了两件事：索引区间是闭区间，而窗口是半开区间；另外，在别的偏移下写入的记录可能按 UTC 落进了区间，按它自己的本地周却在窗口之外。

横轴位置：当日值落在 `daysBetween(首周周一, 该日)` 所在的那一天，周均点落在该周的中点。图表因此不需要做任何日期运算。

否决「在图表里按 UTC 毫秒差算横坐标」：那会把日长算术带到 `timeWindow` 之外，约束扫描会拦下；而且同一条记录按毫秒算出的位置，可能与它按本地日界分组得到的那一天对不上。

### D6 预填值：窗口内的最新一条，窗口为空时退回全表

体重页读出 12 周窗口后，预填值取其中最近一个当日值。窗口为空时，再用 `list()` 读全表，取测量时刻最晚的一条——用户隔了三个月再来，也照样能拿到预填值。只有这种兜底情形才会读两次。

两种读取都能写成一条 `SELECT ... WHERE`：一条按 `measured_at` 取区间，一条按 `user_id` 取全部未删除记录，排序与取最大值都在内存中完成。

否决「每次都读全表」：眼下的数据量撑得住，但 `body_metric` 没有保留期，会无限增长，而 `measured_at` 索引正是为窗口读取建的。

### D7 三条命令，按幂等键定位

| 命令 | 载荷 | 行为 |
| --- | --- | --- |
| `body_metric/record` | `client_id`、`weight_kg` | 写入 `measured_at = ctx.now.iso`、`note = null`。同一 `client_id` 已存在（含墓碑）时原样返回既有主键，不写第二条 |
| `body_metric/update` | `client_id`、`weight_kg` | 经 `withAuditForUpdate` 只改 `weight_kg`。记录不存在或已删除时不写入，返回 false |
| `body_metric/remove` | `client_id` | 软删除 |

按幂等键定位的函数，与幂等键格式的校验，一起从 `commands/workoutLog.ts` 迁出成命令层的共用函数，按表名参数化。运动与体重的命令都改用它。

`update` 拒绝墓碑，是因为改一条已删除的记录没有任何读者，而编辑页本来就把墓碑当作不存在。运动记录的 `update` 不做这项检查；本 change 不改它的行为。

### D8 快速记录的幂等键随成功轮换

幂等键在记录入口挂载时生成一次。写入失败后重试沿用同一个，成功后立即换新。

快速记录停留在同一页、反复使用；不轮换的话，用户当天第二次记录会被当成第一次的重复提交而静默吞掉。写入期间按钮禁用，连点产生的两次提交带的是同一个键，命令层只认第一次。

### D9 单位是 URL 查询参数，不落库

单位存在 `/weight?unit=jin` 里。切换单位时替换当前浏览记录，不新增一条；明细的链接带上它进入 `/weight/:id?unit=jin`，编辑页返回时再带回去。底部导航链接到不带参数的 `/weight`，应用重新打开时落在 `/`，两种情形都回到 kg。参数缺失或取值不合法时，按 kg 处理。

读写这个参数的逻辑写成一个小 hook，体重页与编辑页共用。

否决「只放在组件状态里」：从斤显示的明细点进编辑页，编辑页会变回 kg；浏览器后退后，体重页同样变回 kg。否决「放在导航的 location state 里」：后退回到的那条历史记录在创建时并没有这份状态。否决 localStorage 与 `app_meta`：那就是持久化了，而 proposal 把持久化推迟到了设置页。

### D10 趋势图自绘 SVG，几何是纯函数

不引图表库。图里只有两组数据、两条固定的坐标轴，引入一个库带来的体积与样式适配成本，都比自绘要高。

几何计算集中在 `features/weight/chartGeometry.ts`，作为纯函数单测。它承载三条规则：

- **纵轴范围**：取全部绘制值的最小与最大值，上下留白；跨度不足 1 kg 时，补足到 1 kg，免得一条平稳的序列被拉伸成剧烈起伏。
- **折线分段**：遇到没有周均的周就断开，每一段只连接相邻且都有周均的周；孤立的周均只画点。
- **横坐标**：由 D5 的天数与周序号换算而来，不接触日期。

颜色只用既有的设计令牌：周均线用 `--accent`，当日值散点用 `--fg-muted`，刻度文字用 `--fg-muted`。这些令牌已经通过对比度测试，深浅色模式随 `light-dark()` 自动切换。

无障碍：SVG 带 `role="img"` 与概括图表范围、本周状态的 `aria-label`。图表下方的明细就是这组数据的完整文本形态。

否决 canvas：它没有 DOM，测试断言不到点与线，读屏也读不到内容。

### D11 记录入口吸底，录入与编辑共用一个步进组件

页面自上而下依次是：标题、本周状态（周均或「本周数据太少」）、趋势图（或一句话空状态）、明细。记录入口固定在底部导航之上；页面内容底部留出与入口等高的空白，免得明细的最后一行被挡住。

步进组件包含减、数值输入、加与单位切换，同时服务快速记录与编辑页。两处的规则（D1、D2）完全相同，差别只在提交调用哪条命令。

数值输入用文本框加 `inputmode="decimal"`，而不用 `type="number"`。后者会接受 `1e2` 这类写法，并且在输入未完成时把值报告为空串，「离开输入框时规整并回显」就无法可靠实现。

### D12 两个编辑页都按记录自带的偏移显示自然日

日期与时刻都必须由记录自带的 `tz_offset_minutes` 换算得出：日期用 `dayKeyOf`，时刻用 `clockTimeOf`，两者传入同一个偏移。

不能取时刻字段的前 10 个字符当日期：那是 UTC 日期。运动编辑页现在就是这么写的——`logged_at` 的 UTC 日期，配上本地时刻。东八区本地 07:30 写入的记录，UTC 时刻是前一天 23:30，编辑页因此显示「10 月 30 日 07:30」，而列表把它归在 10 月 31 日那一组。同一条记录在两个页面上分属两天。

修正的做法是把「10 月 30 日」的格式化函数提到 `shared/`（D13），两处都传入记录自带的偏移求自然日。日期与列表的分组于是走同一套换算，不可能指向两天。

体重编辑页 `/weight/:id` 按主键读取记录；读到墓碑或读不到时，显示「这条记录不存在」。删除采用二次确认，确认文案写明后果：不再显示，导出也不含。

### D13 保存失败提示与日期标签提为共享

- **保存失败提示**：从 `WorkoutCardForm` 中提出，放到 `shared/`，由运动表单、快速记录与体重编辑页共用。它按失败原因选文案，并固定渲染「导出数据」「重试」两个出口。`shared/` 不导入命令层，因此由调用方从 `StorageWriteError` 取出原因后传入。失败原因的枚举移到 `entities/`，存储层与共享组件引用同一份定义。
- **日期标签**：「10 月 30 日」的格式化目前是运动列表页的私有函数，体重明细要用同样的格式，因此一并提到 `shared/`。

### D14 `weight_add` 在记录成功后发出

快速记录在 `body_metric/record` 成功后发出事件，调用方式是发出即不管，失败照例被吞掉。

- `prefill`：保存时如果没有预填值，记为 `none`；保存值等于预填值记为 `kept`，否则记为 `changed`。两者都是网格值，可以直接比较相等。
- `unit`：保存时的显示单位。

修改与删除不发这个事件：PRD 定义它记的是「记录体重」，修改与删除另算。

## 目录与分层

```
页面   features/weight/  WeightPage（/weight）、WeightEditorPage（/weight/:id）、
                         WeightStepper、WeightChart、chartGeometry、单位参数 hook
        │  读：@/storage 只读视图（bodyMetricRepo.query / list / get）
        │  写：@/commands 的 applyCommand
        │  算：@/domain（当日值、周均、换算、分组）、@/stats（窗口、周标识、天数）
        ▼
命令   commands/bodyMetric.ts（三条命令）、commands 共用的幂等键定位
        │  @/storage/internal：Repository 写方法、审计字段注入
        ▼
Repo   storage/repositories → storage/indexeddb/**
```

禁止的跨层调用：

| 位置 | 禁止 | 拦截方式 |
| --- | --- | --- |
| `features/weight/**` | 导入 `storage/indexeddb/**`、`storage/internal`、`storage/telemetry` | ESLint |
| `features/weight/**` | 调用 Repository 的 `put` / `remove` / `purge` / `clear` | 只读视图在类型上没有这些方法；约束测试扫描 |
| `domain/bodyMetric.ts`、`domain/dayGroups.ts` | 导入存储、命令与埋点 | 架构测试 |
| `stats/timeWindow.ts` 之外 | 任何日界、周界与日长算术 | 约束测试扫描 |
| `shared/**` | 导入命令层与存储层 | 目录约定；失败原因由调用方传入（D13） |

## 12 条可迁移性约束的落地与自检

| # | 本 change 的落地 | 自检 |
|---|---|---|
| 1 | 体重页与编辑页只经 `@/storage` 读、经 `@/commands` 写 | `constraints.test.ts` 扫描 `indexedDB` 仍只出现在 `storage/indexeddb/**`，新页面不导入数据库实现 |
| 2 | 主键由写入包装层生成；幂等键由页面用 v7 生成 | 既有断言：不出现 `crypto.randomUUID` |
| 3 | `user_id` 由写入包装层注入，命令与页面都不出现该字段 | `constraints.test.ts` 断言 `'local'` 只出现在 `storage/**` |
| 4 | `version` 恒为 1，修改走 `withAuditForUpdate` | 命令单测断言修改后 `version` 不变 |
| 5 | 删除走软删除；`body_metric` 没有任何物理删除路径 | 命令单测断言 `deleted_at` 已写入、记录仍可按主键取到 |
| 6 | 周界与日差算术只在 `timeWindow`，本 change 在其中新增三个函数 | 日界与周界的算术断言；`domain/` 与 `features/` 中没有日期加减 |
| 7 | 不涉及图片 | 既有断言继续通过 |
| 8 | 窗口读取 = `measured_at` 区间 + 内存过滤；预填兜底 = 全表 + 内存取最大 | 新增用例断言两种读取都能写成一条 `SELECT ... WHERE` |
| 9 | 三条命令登记进 `COMMANDS`；页面不调用 Repository 写方法 | 写入口断言；每条命令执行后 `pending_ops` 恰好新增一条 |
| 10 | 不改迁移链；网格校验是对版本 1 字段规格的收紧 | `db.test.ts` 与迁移测试继续通过 |
| 11 | 导出的 `weight_kg` 是网格值，往返一致 | `roundTrip.test.ts` 增加体重记录的用例 |
| 12 | 规整、步进、换算、当日取值、周均、分组都是纯函数 | 架构测试的分层断言；单测不初始化数据库 |

本 change 没有偏离本地优先架构，也没有偏离任何一条约束。

## Risks / Trade-offs

- **不能补记** → 漏称的日子补不回来，有效日更难凑满 3 天。缓解：本周提示给出已记录的天数，用户知道还差几天；补记的需求出现时，再单独评估它对周均的影响。
- **单位不记忆** → 常用斤的用户每次从导航进入都要切一次。缓解：`weight_add.unit` 会给出斤的使用比例，作为在设置页做持久化的依据。
- **明细只覆盖 12 周** → 更早的记录在界面上看不到。缓解：这些记录不会被清理，导出时可以拿到。
- **窗口起点附近的时区差** → 用户在 12 周前那个周一零点前后几个小时内跨时区写入的记录，按 UTC 区间取数时可能漏掉。只涉及这样的边缘样本，运动列表做的是同样的取舍。
- **通用化分组会触及运动模块** → 运动的分组与列表测试保留原有断言，只调整调用形状；断言一条不删。
- **运动编辑页的日期会变** → 东八区凌晨写入的那部分记录，编辑页的日期会从「昨天」变成「今天」。这是修正而不是回归：列表早就把它们归在今天，两个页面对不上才是原来的错。修复只动编辑页，列表的分组没有受影响，也不需要迁移。
- **自绘图表的维护成本** → 以后加目标浅色带（FR-W03）要自己画。缓解：几何都集中在一个纯函数模块里，目标带只是多画一个矩形。

## Migration Plan

不需要迁移：不新增字段、不新增表，`schema_version` 保持 1。回滚就是还原代码；新命令写入的记录都是网格值，在收紧之前的字段规格下同样合法。

## Context

数据层已经按 6 张业务表落地，运动记录的实体与项目卡片规格在上一轮定义完毕。本 change 第一次往 `workout_log` 写真实数据，现状里有四点决定方案形状：

1. **Repository 只有 `put` / `remove` / `clear` 三个写方法。** `remove` 写 `deleted_at`，`clear` 清整表，都不适合「删掉一批超期记录、其余留下」。
2. **日界算术只在 `stats/timeWindow.ts` 一处。** 按自然日分组、最近 30 天窗口、180 天截止时刻都必须是它的调用方，不能各写一遍。
3. **写操作只能经命令层。** 启动清理也要是一条命令，否则它就绕开了 `pending_ops` 与事务边界。
4. **页面通过 `@/storage` 只拿得到只读方法。** 写方法在类型上就不存在，这决定了每一处写得先在命令层开口。

## Goals / Non-Goals

**Goals:**

- 一条记录从填写到出现在列表不超过两次点击，且在断网时照常可用
- 30 天展示窗口、180 天保留期、四档展开三者互不混淆，各有独立参数
- 分组、摘要、填充计数全部是纯函数，可脱离数据库单测
- 启动清理失败不影响打开应用

**Non-Goals:**

- 不做语音、不做当日值、不做统计看板、不做项目名联想
- 不改实体结构，不写迁移，不新增依赖
- 不改命令总线的形状，只新增命令定义

## Decisions

### D1 批量删除落在 Repository 契约里，而不是另起一个清理服务

`Repository.purge(ids: readonly Uuid[], tx?)`：按主键集合物理删除，返回删除条数。

否决「加一个独立的 `retention` 模块直接拿数据库连接」：那会让存储访问多出第二个入口，而收敛到 Repository 是这一层存在的全部意义。落在契约里，换 MySQL 时它对应一条 `DELETE ... WHERE id IN (...)`，不需要额外适配。

方法只接受主键集合、不接受查询条件：判断「哪些记录超期」需要日界算术，那属于 `stats/` 与命令层，存储层不该知道保留期是几天。

### D2 启动清理是一条命令

`workout_log/purge_expired`：命令内部先按 `logged_at` 取上界截止时刻之前的记录，把这些记录的主键交给 `purge`，同一事务内完成。

否决「在 AppShell 里直接调 Repository」：那绕开写入口，也不会留下 `pending_ops`。启动路径与用户操作走同一条写通路，清理才能被导出、被审计、被将来的离线队列看见。

截止时刻由 `stats/timeWindow` 计算：以当前时刻为终点、往前 180 个自然日，按设备当前偏移取那一刻的 UTC 时刻。命令只做「按上界取数 → 交给 purge」，不做日期加减。

### D3 清理在进入主界面前执行，失败不影响启动

位置选在同意之后、路由渲染业务页之前。再早没有意义——未同意时不该碰业务数据；再晚则用户会先看到超期记录再看到它们消失。

失败一律吞掉并继续启动。清理是维护动作，不是用户提交的动作：它失败时用户没有可做的补救，弹一个错误只会让人以为应用坏了。

不走 `pending_ops` 之外的额外记录：清理本身就是一条命令，日志里自然有一条。

### D4 分组与摘要放在 `domain/`，日界来自 `stats/`

```
stats/timeWindow.ts
  recentDayInterval(now, tzOffsetMinutes, days)  -> Interval
  retentionCutoff(now, tzOffsetMinutes, days)    -> IsoUtc

domain/workoutLog.ts
  groupByDay(logs)            -> { day: DayKey, logs: WorkoutLog[] }[]
  daySummary(logs)            -> { count, itemNames }
  filledMetricCount(log)      -> 0..items.length
```

三个域函数的入参是记录数组，不读存储、不取当前时间。`groupByDay` 内部用 `dayKeyOf(log.logged_at, log.tz_offset_minutes)` 归组——按记录自带的偏移判定，用户飞到另一个时区后旧记录仍属于当时那一天。组内按 `logged_at` 倒序，同刻按 `id` 倒序兜底，保证结果确定。

`filledMetricCount` 数的是「至少填了一项指标的卡片数」，与指标填充率的分子口径一致；它不回答「这张记录是否含指标」那个布尔问题——那个由调用方比对 `> 0` 得到。

### D5 四档展开是界面状态，不落库

展开档位存在页面 state 里，刷新回到 30 天。它是一次查看行为，不是用户设置：记住它会让下次打开时看不到最近的记录，而这正是列表最主要的用途。

`history_expand` 事件在点击那一刻发出，属性是**展开后**的目标天数，不是增量。

### D6 卡片表单一份，录入与编辑共用

`features/workout/` 下的卡片编辑器同时服务新建与编辑：两者字段相同、校验相同、布局相同，差别只在提交调哪条命令与顶部标题。

组件内部管理卡片数组，不引入表单库。校验在提交时一次性跑完并把问题定位到卡片与字段，不在输入过程中实时打断——训练间隙输入，实时报错会把「还没填完」误判成「填错了」。

### D7 编辑页只读时间与来源

编辑页展示 `logged_at` 与 `input_source`，不提供编辑入口。`input_source` 只读的理由是它记录的是这条记录**当初怎么进来的**，改它会让语音占比这个指标失真；`logged_at` 只读的理由在提案的差异表里。

### D8 删除二次确认，确认框说明后果

删除是真删除（软删除）而非隐藏，确认框必须写明「删除后不再显示，导出文件也不含这条记录」。不额外提供回收站：PRD 没要求，且超期记录本来就会被清理，回收站会让用户以为数据可以永久留着。

### D9 保存失败的提示复用既有的两种出口

写入失败时按 `StorageWriteError.reason` 分派：配额满提示「先导出再清理历史图片」，其余提示通用原因。两个出口固定为「导出数据」（跳到设置下的导出页）与「重试」（停留在当前页重试同一次提交）。

页面在失败时**不**清空已填写的内容，也不跳转：用户刚输入的东西比任何提示都重要。

## Risks / Trade-offs

- **启动清理与首屏渲染竞争** → 清理在渲染前完成，但失败不阻塞；记录多留一天没有损害。
- **`purge` 扩大了写能力** → 只接受主键集合、只经 `storage/internal` 暴露，页面在类型上拿不到；用途在注释里写死为保留期清理。
- **四档展开不记忆** → 刷新回到 30 天。这是有意为之，见 D5。
- **编辑页不可改时间** → 用户录错日期时无法就地修正，只能删掉重录。PRD 明确时间由程序写入，这里跟随该约束；若日后确有此需求，需要单独评估它对周统计的影响。
- **卡片表单不做实时校验** → 用户可能提交后才发现某张卡片有问题。用提交时一次性报错换取输入过程中不被打断。

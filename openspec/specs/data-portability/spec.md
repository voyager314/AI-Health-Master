## Purpose

让用户随时能把全部数据带走、带回、或彻底删除：JSON 导出作为完整且可反向导入的迁移载体，CSV 导出供用户自行查看，导入用于换设备或从浏览器清缓存中恢复，清空用于行使删除权。数据只存在本机，浏览器清理缓存或更换设备都会让它消失，导出文件因此是数据丢失的唯一兜底，也是将来迁到服务端数据库时唯一的存量迁移载体。

## Requirements

### Requirement: FR-S02.1 全量 JSON 导出

用户必须（SHALL）能一键导出全量数据为单个 JSON 文件。导出文件的结构必须与内部实体结构一致——字段名、字段类型、嵌套关系均不做转换——并在顶层携带 `schema_version` 与导出时刻。

导出范围：9 张业务表与 `analytics_event`，排除已软删除的记录。`pending_ops` 禁止导出（它是写入日志，重放会产生重复写入）。

#### Scenario: 导出产生完整 JSON
- **GIVEN** 本地存在各类业务记录
- **WHEN** 用户点击导出并确认
- **THEN** 下载一个 JSON 文件，含 9 张业务表与 `analytics_event` 的全部未删除记录
- **AND** 顶层含 `schema_version` 与导出时刻

#### Scenario: 导出结构等于内部结构
- **GIVEN** 一条业务记录
- **WHEN** 对比它在库中的结构与在导出文件中的结构
- **THEN** 字段名、字段类型与嵌套关系完全一致
- **AND** `id`、`client_id`、`user_id`、`version` 与审计时间字段均在其中

#### Scenario: 写入日志不导出
- **GIVEN** `pending_ops` 中有记录
- **WHEN** 导出全量数据
- **THEN** 导出文件中不含 `pending_ops`

#### Scenario: 已删除记录不导出
- **GIVEN** 一条已软删除的记录
- **WHEN** 导出全量数据
- **THEN** 导出文件中不含这条记录

#### Scenario: 空库也能导出
- **GIVEN** 本地尚无任何业务记录
- **WHEN** 用户导出
- **THEN** 得到一个结构合法、各表为空数组的 JSON 文件，不报错

#### Scenario: 导出后记录时刻
- **GIVEN** 一次成功的导出
- **WHEN** 检查 `app_meta`
- **THEN** `last_export_at` 被更新为本次导出时刻

### Requirement: FR-S02.2 CSV 导出

用户必须（SHALL）能导出 CSV 以便自行用表格软件查看。CSV 为**单向导出**，不作为导入格式，不要求能反向导入。每张业务表导出为独立的 CSV 表格，嵌套关系以外键列表达。

#### Scenario: CSV 按表导出
- **GIVEN** 本地存在业务记录
- **WHEN** 用户导出 CSV
- **THEN** 得到按业务表拆分的 CSV 内容，首行为列名
- **AND** 嵌套关系以外键列表达

#### Scenario: CSV 不被接受为导入输入
- **GIVEN** 用户在导入入口选择了一个 CSV 文件
- **WHEN** 提交
- **THEN** 提示仅支持 JSON 导入文件
- **AND** 数据库未发生任何变更

### Requirement: FR-S02.3 清空全部数据

用户必须（SHALL）能清空本地全部数据，且必须经二次确认。清空是本能力中唯一允许物理删除的操作，必须清除全部 12 个 store（含 `pending_ops`、`blob`、`analytics_event`）与同意记录。

#### Scenario: 清空需二次确认
- **GIVEN** 用户点击「清空全部数据」
- **WHEN** 尚未在确认弹窗中确认
- **THEN** 数据未被删除

#### Scenario: 确认后全部清空
- **GIVEN** 用户在确认弹窗中确认
- **WHEN** 清空执行完成
- **THEN** 全部 12 个 store 被清空
- **AND** 应用回到首次使用状态，重新要求告知同意
- **AND** 清空完成后写入一条记录本次清空的 `clear_data` 埋点事件（见 `local-telemetry`），它是 `analytics_event` 中唯一的记录

#### Scenario: 取消不产生影响
- **GIVEN** 用户在确认弹窗中取消
- **WHEN** 弹窗关闭
- **THEN** 全部数据保持原样

### Requirement: FR-S07.1 从 JSON 导入恢复

用户必须（SHALL）能选择一个导出的 JSON 文件，把全部数据恢复到本地。导入语义为**整库替换**：成功导入后，本地数据等于文件内容。

导入必须按下列顺序执行，任一步失败即中止且不改动数据库：

1. 校验文件的全部内容（结构、`schema_version` 兼容性、每条记录的必需字段）
2. 向用户二次确认「这将替换当前全部数据」
3. 自动导出当前数据为备份文件
4. 清空数据库
5. 写入文件内容

#### Scenario: 导入恢复全部数据
- **GIVEN** 一个结构合法、版本兼容的导出文件
- **WHEN** 用户导入并确认
- **THEN** 本地数据等于文件内容
- **AND** 导入前的数据已先被导出为备份文件

#### Scenario: 导入需二次确认
- **GIVEN** 用户选择了一个合法的导入文件
- **WHEN** 尚未确认「替换当前全部数据」
- **THEN** 数据库未发生任何变更

#### Scenario: 校验先于改动
- **GIVEN** 一个在第 300 条记录处字段缺失的导入文件
- **WHEN** 用户导入
- **THEN** 校验阶段即报错并指出问题位置
- **AND** 数据库未被清空，原数据完好

#### Scenario: 文件损坏被拒绝
- **GIVEN** 一个非 JSON 或 JSON 语法错误的文件
- **WHEN** 用户导入
- **THEN** 提示文件无法解析
- **AND** 数据库未发生任何变更

#### Scenario: 版本不兼容被拒绝
- **GIVEN** 一个 `schema_version` 高于当前应用支持版本的导入文件
- **WHEN** 用户导入
- **THEN** 提示版本不兼容并说明需升级应用
- **AND** 数据库未发生任何变更

#### Scenario: 旧版本文件按迁移链升级
- **GIVEN** 一个 `schema_version` 低于当前版本的导入文件
- **WHEN** 用户导入
- **THEN** 文件内容经顺序迁移升级到当前版本后写入
- **AND** 导入成功

#### Scenario: 缺失的图片引用解析为已清理
- **GIVEN** 一个业务记录含 `storage_ref`、但文件不含对应 blob 的导入文件
- **WHEN** 导入完成后解析该引用
- **THEN** 返回「已清理」状态
- **AND** 业务记录本身完好可读

### Requirement: FR-S07.2 导出与导入的往返一致性

「导出 → 清空 → 导入」之后，本地数据必须（SHALL）与导出前完全一致：记录条数逐表相等，且每条记录的全部字段值（含 `id`、`client_id`、`user_id`、`version` 与审计时间字段）逐一相等。

导出文件是数据唯一的迁移载体：用户换设备、浏览器清缓存、将来迁到服务端，都只能靠它把数据带回。因此往返一致性是发布前的必备检查，不是可选项。

#### Scenario: 往返后数据完全一致
- **GIVEN** 本地存在覆盖全部 9 张业务表的记录
- **WHEN** 依次执行导出、清空、导入
- **THEN** 逐表记录条数与导出前相等
- **AND** 每条记录的全部字段值与导出前相等

#### Scenario: 时间字段不因往返漂移
- **GIVEN** 一条含时间字段与 `tz_offset_minutes` 的记录
- **WHEN** 经过导出与导入的往返
- **THEN** 时间字段字符串与 `tz_offset_minutes` 与原值完全相同，不发生时区转换

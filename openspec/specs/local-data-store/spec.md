## Purpose

定义 AI Health Master 全部业务数据在用户设备上的持久化契约：实体结构、记录标识与审计字段、时间表示、软删除语义、schema 版本与迁移、图片二进制的存放方式，以及写入失败时的行为。本能力是「本地优先」架构的地基，也是将来替换为服务端数据库时唯一需要改动的层。

## Requirements

### Requirement: FR-S01 业务数据本地持久化

业务数据必须（SHALL）存于用户设备的本地数据库（IndexedDB），禁止上传服务端。数据必须在页面刷新、浏览器重启、应用从主屏冷启动后依然存在。

本能力覆盖 9 个 store，分两类：

**6 张业务表**（`user_id` / `version` / 审计字段契约适用于这 6 张）：
`workout_log`、`body_metric`、`meal`、`meal_item`、`target`、`app_meta`

**3 个非业务 store**（不适用业务表字段契约）：
`pending_ops`（写入日志）、`blob`（图片二进制）、`analytics_event`（本地埋点）

9 个 store 的结构由存储层统一定义；表中业务数据的写入由使用它们的各项功能分别实现。

运动模块只有 `workout_log` 一张表：动作库、训练单、训练单动作与组记录随「只做记录」的产品定位一并取消，运动项目作为记录内的嵌套值存放（见 FR-S01.7）。

#### Scenario: 数据跨会话存活
- **GIVEN** 用户已在本地产生业务记录
- **WHEN** 用户刷新页面或完全关闭浏览器后重新打开应用
- **THEN** 该记录仍可读出，内容与写入时完全一致

#### Scenario: 业务数据不出设备
- **GIVEN** 应用处于任意业务操作过程中
- **WHEN** 检查应用发出的全部网络请求
- **THEN** 请求中不含任何业务记录内容

#### Scenario: 表清单恰好 6 张业务表
- **GIVEN** 一个全新安装的本地库
- **WHEN** 列出其全部 store
- **THEN** 业务表恰为上述 6 张
- **AND** 不存在 `exercise`、`workout`、`workout_exercise`、`set_entry`

### Requirement: FR-S01.1 记录标识与审计字段契约

6 张业务表的每条记录必须（SHALL）含下列字段，缺任一字段即视为不符合本需求：

| 字段 | 规则 |
| --- | --- |
| `id` | UUID v7，时间有序。禁止自增 ID，禁止退化为 UUID v4 |
| `client_id` | 客户端生成的幂等键，可与 `id` 同值 |
| `user_id` | 本期固定为字符串 `'local'`，且必须建索引 |
| `version` | 整数，本期恒为 `1` |
| `created_at` / `updated_at` | 写入与每次更新时刷新 |
| `deleted_at` | 未删除时为空 |

#### Scenario: 主键为时间有序 UUID
- **GIVEN** 连续创建的两条业务记录 A 与 B（A 先于 B）
- **WHEN** 比较两者的 `id` 字符串
- **THEN** A 的 `id` 字典序小于 B 的 `id`
- **AND** `id` 符合 UUID v7 的版本位

#### Scenario: 审计字段齐备
- **GIVEN** 任意一张业务表
- **WHEN** 检查其记录结构与索引
- **THEN** 上表 7 个字段全部存在，且 `user_id` 有索引

#### Scenario: 更新刷新时间戳
- **GIVEN** 一条 `created_at` 与 `updated_at` 相同的记录
- **WHEN** 该记录被更新
- **THEN** `updated_at` 变为更新时刻，`created_at` 保持不变

### Requirement: FR-S01.2 时间表示统一为 UTC

所有时间字段必须（SHALL）存为 UTC ISO 8601 字符串；用户当时的时区偏移必须另存于独立字段 `tz_offset_minutes`。禁止存储带时区偏移的时间字符串，禁止存储本地时间字符串，禁止存储时间戳数字。

#### Scenario: 时间字段格式
- **GIVEN** 任意一条带时间字段的记录
- **WHEN** 读出其时间字段
- **THEN** 取值为以 `Z` 结尾的 UTC ISO 8601 字符串
- **AND** 同一记录上存在独立的 `tz_offset_minutes` 整数字段

#### Scenario: 跨时区写入保留原时区
- **GIVEN** 设备时区为 UTC+8
- **WHEN** 写入一条记录
- **THEN** 时间字段为 UTC 表示
- **AND** `tz_offset_minutes` 为 `480`

### Requirement: FR-S01.3 软删除

删除业务记录必须（SHALL）写 `deleted_at` 而非物理移除。已软删除的记录在所有常规查询与导出中必须被排除，但在数据库中必须依然存在。

物理删除只允许下列三种情形：

1. 「清空全部数据」（见 `data-portability`）；
2. 图片 blob 的清理（见 FR-S01.5）——软删除不释放配额，留下悬空引用反而要额外处理；
3. `workout_log` 超过保留期的启动清理（见 FR-S01.8）。

#### Scenario: 删除后记录仍在库中
- **GIVEN** 一条已存在的业务记录
- **WHEN** 用户删除它
- **THEN** 该记录的 `deleted_at` 被写入删除时刻
- **AND** 数据库中仍能按主键取到这条记录

#### Scenario: 已删除记录不出现在查询与导出中
- **GIVEN** 一条已软删除的记录
- **WHEN** 列出该表记录或导出全量数据
- **THEN** 结果中不含这条记录

#### Scenario: 保留期外的记录被物理删除
- **GIVEN** 一条 `logged_at` 早于 180 个自然日的运动记录
- **WHEN** 应用启动并执行保留期清理
- **THEN** 该记录从库中物理移除
- **AND** 它不再出现在导出文件中

### Requirement: FR-S01.4 schema 版本与顺序迁移

本地数据库必须（SHALL）记录 `schema_version`。应用启动时必须按版本顺序执行迁移脚本，每个版本对应且仅对应一条迁移。执行任何迁移之前，必须先自动导出一份当前数据的备份文件。迁移失败时禁止让数据库停留在中间状态。

本版的结构版本为 `1`。该版本尚未对外发布，其迁移内容直接描述当前的 6 张业务表与 3 个非业务 store；版本号一经随正式版本发布即冻结，此后任何结构调整都必须新增一个版本。

#### Scenario: 迁移前自动备份
- **GIVEN** 本地 `schema_version` 低于应用期望版本
- **WHEN** 应用启动
- **THEN** 先产生一份当前数据的备份文件，再执行迁移

#### Scenario: 按版本顺序迁移
- **GIVEN** 本地 `schema_version` 为 1，应用期望版本为 3
- **WHEN** 应用启动
- **THEN** 依次执行 1→2 与 2→3 两条迁移，顺序不可颠倒
- **AND** 完成后 `schema_version` 为 3

#### Scenario: 迁移失败不留中间状态
- **GIVEN** 一条迁移脚本在执行中抛错
- **WHEN** 迁移中断
- **THEN** 数据库回到迁移前的版本与内容
- **AND** 向用户说明失败原因并指出备份文件位置

#### Scenario: 版本相同时不迁移
- **GIVEN** 本地 `schema_version` 等于应用期望版本
- **WHEN** 应用启动
- **THEN** 不执行迁移，不产生备份文件

#### Scenario: 全新安装建出 9 个 store
- **GIVEN** 本地没有任何数据库
- **WHEN** 首次打开应用
- **THEN** 建出 6 张业务表与 3 个非业务 store
- **AND** 不需要任何升级步骤

### Requirement: FR-S01.5 图片二进制独立存放

图片必须（SHALL）以二进制形式存于独立的 `blob` store；业务记录中只允许存字符串引用 `storage_ref`，本地格式为 `local://<uuid>`。禁止把图片以 base64 或二进制形式嵌入业务记录。

引用的目标 blob 可能已不存在（被清理策略移除，或从不含 blob 的备份导入）。解析一个 `storage_ref` 必须返回三态之一：命中、**已清理**、格式非法。禁止因 blob 缺失而抛错或让调用方得到空值歧义。

#### Scenario: 业务记录只存引用
- **GIVEN** 一条关联图片的业务记录
- **WHEN** 检查该记录的字段
- **THEN** 图片字段为 `local://<uuid>` 形式的字符串
- **AND** 记录中不含任何 base64 字符串或二进制字段

#### Scenario: 引用的 blob 已不存在
- **GIVEN** 一条业务记录的 `storage_ref` 指向一个已不在 `blob` store 中的 uuid
- **WHEN** 解析该引用
- **THEN** 返回「已清理」状态
- **AND** 业务记录本身保持完好、可正常读写

#### Scenario: 引用格式非法
- **GIVEN** 一个不符合 `local://<uuid>` 格式的 `storage_ref`
- **WHEN** 解析该引用
- **THEN** 返回「格式非法」状态，与「已清理」可区分

### Requirement: FR-S01.6 写入失败必须可感知

本地存储写入失败（最常见为存储配额已满）时，必须（SHALL）向用户明确提示失败原因与可操作的下一步（先导出数据、再清理历史图片），并提供重试入口。禁止静默丢弃用户数据，禁止在界面上表现为「已保存」。

#### Scenario: 配额满时提示而非静默失败
- **GIVEN** 本地存储配额已满
- **WHEN** 用户的一次写操作被拒绝
- **THEN** 界面提示写入失败与原因
- **AND** 给出「导出数据」与「重试」两个入口
- **AND** 该操作不被标记为已保存

#### Scenario: 失败后数据不残缺
- **GIVEN** 一次涉及多条记录的写操作中途失败
- **WHEN** 失败发生
- **THEN** 这批记录要么全部写入、要么全部未写入

### Requirement: FR-S01.7 运动记录的嵌套项目卡片

`workout_log` 必须（SHALL）含下列字段：

| 字段 | 规则 |
| --- | --- |
| `logged_at` | 记录产生时的设备本地时刻，按 UTC 存储，精确到秒，由程序写入，用户不可编辑 |
| `tz_offset_minutes` | 写入当时的时区偏移，东为正 |
| `input_source` | `manual`（手动填写）或 `voice`（语音提交），用于统计语音记录占比 |
| `items` | 项目卡片数组，至少 1 张，顺序即数组下标 |

项目卡片 `items[]` 是记录内的嵌套值，禁止（MUST NOT）独立成表、自带主键或被其他记录引用。

卡片字段：

| 字段 | 规则 |
| --- | --- |
| `name` | 必填，不超过 40 字，自由文本，无预设动作库，不做别名归并；同一条记录内允许重复 |
| `sets` | 每组组数，正整数，`null` 表示未填 |
| `reps` | 每组次数，正整数，`null` 表示未填 |
| `weight_kg` | 重量，以 kg 存储，0.5 步进，不小于 0，`null` 表示未填 |
| `note` | 独立描述，不超过 200 字，`null` 表示未填 |

三项指标同时为 `null` 是合法状态，表示用户只记得项目名。卡片只呈现已填写的指标，未填项不显示占位符或默认值。

#### Scenario: 只填项目名是合法记录
- **GIVEN** 一张卡片只有 `name` 为「卧推」，三项指标均为 `null`
- **WHEN** 校验这条记录
- **THEN** 通过校验，且记录可正常保存与读出

#### Scenario: 体重步进不合规被拒绝
- **GIVEN** 一张卡片的 `weight_kg` 为 `80.3`
- **WHEN** 校验这条记录
- **THEN** 校验失败并定位到该卡片的 `weight_kg`

#### Scenario: 组数必须为正整数
- **GIVEN** 一张卡片的 `sets` 为 `0` 或 `2.5`
- **WHEN** 校验这条记录
- **THEN** 校验失败并定位到该卡片的 `sets`

#### Scenario: 未知字段被拒绝
- **GIVEN** 一张卡片带有 `rpe` 或 `duration_sec` 这类未声明的字段
- **WHEN** 校验这条记录
- **THEN** 校验失败并指出该字段名

#### Scenario: 空项目列表被拒绝
- **GIVEN** 一条记录的 `items` 为空数组
- **WHEN** 校验这条记录
- **THEN** 校验失败

#### Scenario: 项目名超长被拒绝
- **GIVEN** 一张卡片的 `name` 长度为 41 字
- **WHEN** 校验这条记录
- **THEN** 校验失败并定位到该卡片的 `name`

#### Scenario: 同一记录内项目名可重复
- **GIVEN** 一条记录含两张 `name` 均为「卧推」的卡片
- **WHEN** 校验这条记录
- **THEN** 通过校验

### Requirement: FR-S01.8 运动记录保留期与展示窗口

运动记录必须（SHALL）保留 180 个自然日。超过保留期的记录在应用启动时物理删除，不提供回收站。

近 30 天展示窗口与 180 天保留期是两个独立参数：30 天窗口只影响查询范围，不触发任何删除；保留期只影响删除，不限制查询能取到多久以前的数据。

自然日边界按记录自带的 `tz_offset_minutes` 计算，不按设备当前时区。

#### Scenario: 展示窗口不删除数据
- **GIVEN** 本地存在 45 天前的运动记录
- **WHEN** 用户查看近 30 天列表
- **THEN** 该记录不出现在默认列表中
- **AND** 它仍留在数据库中，可在保留期内查阅

#### Scenario: 保留期内可查阅
- **GIVEN** 本地存在 150 天前的运动记录
- **WHEN** 用户展开「查看更早」
- **THEN** 该记录可见

#### Scenario: 超期记录在启动时清理
- **GIVEN** 本地存在 181 天前的运动记录
- **WHEN** 应用下次启动
- **THEN** 该记录被物理删除
- **AND** 它不再出现在任何列表与导出文件中

#### Scenario: 已软删除的记录随清理一并移除
- **GIVEN** 一条已软删除且超过保留期的运动记录
- **WHEN** 应用启动并执行清理
- **THEN** 该记录从库中物理移除

#### Scenario: 体重与饮食不受运动记录保留期影响
- **GIVEN** 一条 200 天前的体重记录
- **WHEN** 应用启动并执行清理
- **THEN** 该记录仍在库中
